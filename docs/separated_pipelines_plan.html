Why paired folders were sought — and the new separated per-sample-type pipelines

status: implemented — split engine, augmentation pipeline, preview, tests and docs follow this document · 2026-11-27 · supersedes docs/archive/split_redesign_plan.html

1 · The question, answered directly: why was the plan looking for paired folders?

Short answer: pairing was never a requirement of the classifier or of the augmentation. It was the split-integrity unit of an engine built back when the dataset was LCDMoire-only. LCDMoire stores every scene twice — gt/x.jpg (clean) and moire/x.jpg (real moire), matched by filename — and the code made that (moire, clean) pair the indivisible atom of the whole pipeline: index-aligned folder lists, 1:1 filename binding, pair-level shuffle, twin-integrity tests. When commit 9eafbcf added the AirDroid folders (two flat per-class pools with no twin relation), that atom stopped existing, and list_folder_pairs crashed at data.py:62 ("clean/moire folder lists must be index-aligned: 65 clean vs 104 moire folders"). The previous plan (docs/archive/split_redesign_plan.html) proposed auto-detecting twin folders by identical filename sets — a patch that preserved the old invariant instead of questioning it.

What the pairing actually bought (the honest reasons it existed)

  1. Leak-free evaluation. gt/x.jpg and moire/x.jpg are near-duplicates of the same scene. If the moire twin lands in the test split while the clean twin sits in train, the model has effectively memorized the test scene and only needs to detect the deviation — test metrics inflate. The pair unit made twin leakage impossible by construction, and tests/test_data_split.py:84 pinned it as a guarantee (“every moire/gt twin pair stays inside exactly one split”).
  2. Exact 50/50 class balance in every split, for free. Every pair contributes exactly one clean and one moire sample, so train/val/test were exactly balanced without any balancing machinery.

Where the coupling lived (everything the new design removes)

  • config.py:26-32 documents the pools as index-aligned, filename-matched twin lists;
  • list_folder_pairs (data.py:48-80) enforces it — equal list lengths, identical filename sets, 1:1 binding — the crash site;
  • split_train_val_test (data.py:100-125) shuffles pair lists so twins always land in the same split;
  • samples_from_pairs (data.py:83-88) emits (moire, clean) tuples, coupling the classes at sample level;
  • augmented_moire_dataset coupled them deepest: in balanced mode (the default) the moire half of each batch is partly synthesized from clean sources (train_baseline.py:203-205) — the clean pipeline feeding the moire class — while clean fetches stay clean (parity just fixes labels, augmentation.py:157-162); on the unbalanced path (--no-balance-batches) clean fetches are even converted to moire with a label flip 0→1 (augmentation.py:173-177).

Why your direction is the right architecture

A binary moire detector needs two labeled pools and per-class pipelines, not coupled pairs. Class balance is already enforced where it actually matters — at batch level — by balanced_moire_dataset + balanced_shuffle_sampler (data.py:178-240), which interleave the real clean/moire pools and oversample the smaller one; no pairing is involved. The pools in config.py are already the flat per-class shape the new design wants (65 clean folders, 104 moire folders, any lengths). The only thing pairing provided that nothing else in the codebase replaces is twin integrity — a data-hygiene property, not a correctness requirement. Section 2 quantifies exactly what is traded for removing it.

The honest cost: twin leakage

The two streams are shuffled and cut independently, so twins land independently: P(twins in different splits) = 1 − (0.8² + 0.1² + 0.1²) ≈ 34%; in the metric-relevant direction (one twin in test, the other in train) it is 2 · 0.8 · 0.1 = 16% — roughly 500 of the 3,160 LCDMoire scenes. Test numbers will read somewhat optimistic. Three mitigating facts:

  • The old pair-based design already accepted the same cross-class scene leakage for every AirDroid object (its folders were never pairable).
  • Measured on the actual data: the 160 stems in LCDMoire’s test folders are a subset of the train folders’ stems (160/160 on both the gt and moire sides), as different files (0/160 byte-identical — same scene key, distinct captures). So even the pair-based engine could place the same scene in both train and test via its two folder copies: the twin guarantee was already weaker in practice than the code promised.
  • Batch-level balance — the property that actually drives training — is untouched (balanced batches keep exact 50/50 from real pools).

An optional, off-by-default hash-alignment guard is sketched in §3.7 if evaluation honesty later becomes a priority; it is deliberately not part of this change.

3 · The new design — separated per-sample-type pipelines

The redesign follows your directives as five rules:

  • R1 · Separation. Clean and moire samples are collected, split and augmented as two independent pipelines. The only thing they share is code.
  • R2 · One shared method. Both pipelines call the same augmentation entry point; the sample’s class parameterizes it.
  • R3 · Labels preserved. A sample’s label is fixed once, at collection time, from the pool the file came from (clean folder → 0, moire folder → 1). No augmentation may change it.
  • R4 · Moire gating. Moire-related augmentation (sample_moire_type + MOIRE_GENERATORS) may run only on moire-class samples. Clean-class samples can only receive label-neutral capture-style augmentation (the six imgaug groups + the torchvision train transform).
  • R5 · Untouched evaluation data. Validation and test samples are never affected by any type of augmentation — no moiré draw, no capture-style groups, no train transform. They flow through plain moire_dataset + build_eval_transform (deterministic resize → center-crop → normalize), which is already how the code builds them (train_baseline.py:226, evaluate_baseline.py:131); the redesign pins this as a tested guarantee instead of an implicit side effect.

3.1 · Split redesign (src/spatial_moire/baseline/data.py)

  • list_folder_pairs and its entire contract (index alignment, filename matching, twin binding) are deleted. No pairing detection of any kind remains anywhere in the codebase.
  • New collect_class_samples(folders, label): walks each folder (must exist, must be non-empty — the loud ValueErrors stay), lists images in filename order via list_image_files, and emits {"path", "label"} dicts. The label comes from the pool, never from content or augmentation (R3).
  • New build_split_units(folders, label) builds the split units of one stream:
    • a folder holding ≤ FOLDER_UNIT_MAX_IMAGES (new config constant, default 32) images is one atomic unit — every AirDroid folder qualifies (measured 2–22 images, avg 4.9);
    • a larger folder (LCDMoire: 160 and 3,000) contributes one unit per image, and images sharing a filename stem within one stream merge into a single unit — so the 160 test-folder captures of already-train scenes cannot straddle splits.
  • split_train_val_test keeps its exact signature (clean_folders, moire_folders, train_fraction, val_fraction, test_fraction, seed) — the call sites in train_baseline.py, evaluate_baseline.py and the tests stay untouched. New internals:
    1. validate_split_fractions (unchanged);
    2. clean_units = build_split_units(clean pool, CLEAN_LABEL); moire_units = build_split_units(moire pool, MOIRE_LABEL);
    3. random.Random(seed).shuffle(clean_units) and random.Random(seed + 1).shuffle(moire_units) — two independent shuffles;
    4. per stream: train_count = round(len(units) · train_fraction), val_count likewise, test gets the remainder — the cut is applied to each stream separately;
    5. flatten: each split’s sample list = its clean units’ samples + its moire units’ samples.
  • save_split_manifest gains "algorithm": "per_class_units_v1" (plus the unit threshold), so evaluate_baseline.py can refuse to replay a manifest produced by a different split algorithm instead of silently deriving a different split. Version note: the split-manifest format moves from the implicit pair-based v1 to the labeled per_class_units_v1; existing manifests are invalidated — the first training run after approval regenerates them.
  • Unchanged on purpose: moire_dataset, balanced_moire_dataset, balanced_shuffle_sampler, build_train_transform, build_eval_transform — they are already per-class-pool and label-preserving. samples_from_pairs survives only as a small utility used by tests; it no longer participates in the split.

3.2 · Augmentation redesign (src/spatial_moire/baseline/augmentation.py)

  • augmented_moire_dataset becomes the shared, label-preserving, class-aware pipeline (class name kept, contract rewritten). It is the one augmentation entry point both classes call (R2).
  • Index space. balanced=True: exactly balanced_moire_dataset’s interleaved space — even slots address the real clean pool, odd slots the real moire pool, the smaller pool cycles (oversampled). There is no synthesis fallback: an empty moire pool raises ValueError, because balanced batches can no longer be filled from clean sources. balanced=False: walks samples in list order.
  • One shared method, _augment_sample(image, label, rng):
    • label 0 (clean): group augmentation only (when enabled) via apply_group_augmentation — noise, photometric, contrast, blur, dropouts, geometric, all label-neutral. sample_moire_type and MOIRE_GENERATORS are structurally unreachable on this path (R4). Returned label: 0.
    • label 1 (moire): with probability moire_augment_prob, draw a weighted moire type (sample_moire_type) and run its generator on the image — a real moire photo may gain one additional synthesized moire pattern (still moire); then group augmentation. Returned label: 1.
  • Train-split-only scope (R5). The augmented dataset is attached to the train split only, exactly as today (train_baseline.py:182 builds train, :226 builds val). Validation and test datasets stay plain moire_dataset with build_eval_transform — deterministic resize → center-crop → normalize, nothing else — so moire_augment_prob and group_augment cannot reach a val or test sample by construction (evaluate_baseline.py:131 builds the test set the same way).
  • Removed outright: the on-the-fly clean→moire conversion and its label flip (the reassignment to MOIRE_LABEL), and the balanced-mode path that drew clean sources for moire slots. A clean image can no longer become moire anywhere inside the training pipeline.
  • Parameters: augment_prob is renamed moire_augment_prob (default MOIRE_AUGMENT_PROB = 0.5) with new meaning — the probability that a moire-class fetch receives the additional pattern draw. It never applies to clean fetches; 0.0 disables on-the-fly moire synthesis entirely (clean→moire then exists only in generate_moire_samples.py). type_names, seed, group_augment, group_names, num_groups_range are unchanged.
  • train_baseline.py: no call-site changes (same constructor, same flags --moire-augment-prob, --moire-augment-types, --group-augment, --augment-groups, --augment-group-count, --no-balance-batches); only help texts and console prints change — e.g. “a 50% share of moire fetches receives an additional synthesized moire pattern; clean images only receive capture-style groups; labels never change”.
  • preview_train_augmentation.py: selects the first N clean and N moire images with a seeded draw from the first folder of each pool, runs them through the same class pipelines for several passes, and labels gallery rows per class: clean → “groups only” / “untouched” (never moire); moire → “type-augmented + groups” / “groups only” / “untouched”. The paired-scene selection (select_scene_pairs / list_folder_pairs) and the “clean → moire (synthesized)” gallery path disappear.
  • generate_moire_samples.py: unchanged by design. That is the boundary of R4: turning a clean image into moire is sample generation, not pipeline augmentation — it happens offline, writes new moire-class files (moire_<type>__<stem>_vNN.jpg + moire_synthesis_params.json), and those files are moire samples with label 1 the moment their folder is listed in MOIRE_IMAGE_FOLDERS. (Assumption to confirm — §3.7.)

3.4 · Expected numbers (measured on the current pools)

  • Pools: 65 clean folders / 3,583 images · 104 moire folders / 3,545 images · 7,128 total.
  • LCDMoire: 3,160 clean (train 3,000 + test 160) and 3,160 moire; the 160 test-folder stems all also appear in the train folders (as distinct files).
  • AirDroid: 63 clean folders / 423 images (2–22 per folder, avg 4.9) · 102 moire folders / 385 images.
  • Split units: clean = 3,000 stem-merged LCDMoire units + 63 folder units = 3,063 · moire = 3,000 + 102 = 3,102.
  • 0.8 / 0.1 / 0.1 cut per stream ≈ clean 2,450 / 306 / 307 units and moire 2,481 / 310 / 311 units → sample-level split sizes ≈ train 5,700 · val 715 · test 715, each ≈ 50.3% clean / 49.7% moire.
  • Balanced epochs (training): num_slots ≈ 2,866 → ≈ 5,732 items per epoch, every batch exactly 50/50 from real pools.

3.7 · Assumptions and open items (explicitly awaiting your word)

  1. generate_moire_samples.py stays. Offline synthesis remains the only place a clean image becomes moire — it writes new moire-class files rather than relabeling or in-pipeline augmenting a clean sample. If you want that tool removed as well, say so.
  2. moire_augment_prob default. 0.5 now governs the additional pattern draw on real moire fetches only. Prefer 0.0 (on-the-fly moire synthesis fully off; synthesis only offline)? One-line change.
  3. Twin leakage accepted (≈16% of scenes with one twin in test and the other in train) as the price of fully separated pipelines. If it later matters, an off-by-default guard can derive each unit’s split from hash(seed, stem) — twins share stems, so they would coincide without any pairing logic.
  4. Old split_manifest.json files are invalidated by the algorithm change (marker per_class_units_v1); the first training run after approval regenerates them.
  5. R5 needs no new machinery. Validation and test datasets are already built augmentation-free (train_baseline.py:226, evaluate_baseline.py:131); the rule adds tests and documentation, not code paths.
